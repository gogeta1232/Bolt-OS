# Command performance

## Scope and evidence

The October 2026 pass reviewed the execution paths and shared services for all 42 command pieces. All 42 loaded through Sapphire in an offline probe. Targeted tests exercise command acknowledgement, AFK persistence, role search, cache races, profile lookups, statistics and purge scheduling. This is not a live-guild certification of every command branch.

Command success and failure records now include `durationMs` from Sapphire. This measures the command handler, including work it awaits; it excludes work before the handler and detached background work. Compare commands and invocation types separately. A quick confirmation does not prove that background moderation or logging has completed.

No production token, guild or database was used. Discord latency, MongoDB latency, host load and rate-limit queues remain unmeasured here. Defer improves acknowledgement reliability; it does not make the underlying operation faster. Discord requires an initial acknowledgement within three seconds: [interaction responses](https://docs.discord.com/developers/interactions/receiving-and-responding).

## Controlled measurements

Run `npm run build`, then `node work/performance/benchmark.mjs`. The script compares the saved pre-change source with the built implementation using controlled boundaries. It does not connect to Discord or MongoDB. Each burst contains 20 overlapping requests, with a serialized boundary delaying each operation by 5 ms. There are two warmups and eight measured trials. Windows timer resolution affects the elapsed times.

| Scenario                                                            | Before                                                  | After                                                   |
| ------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------- |
| Incomplete guild member cache, 20 simultaneous stats calls          | 20 full member fetches; median 311.96 ms                | 1 full member fetch; median 15.77 ms                    |
| Cold autoresponder cache, 20 simultaneous list calls                | 20 MongoDB queries; median 315.18 ms                    | 1 MongoDB query; median 15.89 ms                        |
| 100 old messages plus 100 recent messages whose bulk deletion fails | Peak 200 individual requests                            | Peak 5 individual requests; same 200 successful deletes |
| AFK set command, successful write                                   | Initial read, write, second read                        | Initial read and write; uses returned stored document   |
| AFK slash command, supplied image download fails                    | Same URL could be downloaded twice                      | One download attempt per invocation                     |
| Role prefix command, 12 words and no matching role                  | Initial member lookup plus 11 speculative split lookups | Initial member lookup only                              |

The first three rows are recorded in `work/performance/results.json`. AFK and role request reductions are verified by command regression tests. These figures describe request amplification and controlled scheduling, not a production speed multiplier.

## Slash and prefix benchmark

Run `npm run build`, `node work/performance/command-probe.mjs`, then `node work/performance/command-benchmark.mjs`. Results are saved to `work/performance/command-results.json`. This executes the actual built handlers for all 42 commands in both styles. Prefix runs include Sapphire's real argument parser and the actual member resolver; the gateway dispatch and precondition pipeline are excluded.

Each of the 84 command/style scenarios has two warmups and eight measured runs in each of two modes: immediate boundary responses and a requested 20 ms delay per boundary call. Windows timers may take longer than 20 ms. The latter is a controlled wait experiment, not a prediction of production latency. Even cache-capable service/manager calls receive that delay; their counts are boundary invocations, not actual REST requests or MongoDB queries.

Discord objects are real library structures with synthetic data: an owner actor, 100 cached members, 25 roles, and three channels. Discord actions, configuration/case/AFK/warning/logging services, snapshot model calls and the image download are controlled fakes. Services themselves, database performance, transport, rate limits, reconnects and large-guild scaling are not benchmarked. No login or MongoDB connection occurs. Discord REST access is rejected and downloads return only a fixture response. Mutable fixture state is recreated for each trial.

The report separates initial acknowledgement, last command response, handler return and completion of tracked detached work. Collector interaction, delayed response deletion and warning modal submission are outside the measurement. Slash `warn issue` opens its modal; prefix `warn` issues the warning, so those two timings cover different amounts of work. The nearest-rank p95 field equals the maximum with only eight samples; the visualization labels it as the slowest observed run, not a reliable production percentile.

The harness checks that the intended mutation or lookup occurs and rejects known failure/usage responses. This is one named successful scenario per command and style, not coverage of every subcommand, authorization outcome, media path or edge case. The benchmark exposed two correctness issues: the slash warning duration label exceeded the builder's limit, and prefix jail-channel parsing discarded the first channel argument. Both have regression tests.

## Sapphire prefix execution

The installed Sapphire 5.5.1 path is message filtering, channel permission checks, mention/regex/configured-prefix detection, command-store lookup, preconditions, `messagePreParse`, then `messageRun`. Bolt retains those framework listeners and permission checks. The framework's typing listener is disabled unless the client enables `typing`; when enabled it handles an emitted event independently rather than blocking `messageRun`. Disabling it would not remove an awaited step in Bolt's handler. See the official [command lifecycle](https://www.sapphirejs.dev/docs/Documentation/api-framework/classes/Command/) and [argument parser](https://www.sapphirejs.dev/docs/Documentation/api-framework/classes/Args/).

Warm configured-prefix lookups now return synchronously from the existing configuration cache. The separate unbounded prefix map has been removed. Configuration keeps its five-minute TTL and 10,000-guild limit; successful writes refresh it, guild removal invalidates it, and an older pending read cannot overwrite a newer write or repopulate an invalidated entry. Cold concurrent lookups continue to share one database query. Sapphire still awaits the prefix hook and retains its normal dispatch semantics.

`roleinfo`, `userinfo` and `userbanner` now use `Args.pickResult` once rather than `peekResult` followed by `pick`. The installed Lexure parser consumes a token only when conversion succeeds; tests verify multi-word fallback input remains intact. Successful member conversions call Bolt's resolver once instead of twice, and role conversion invokes the role manager once instead of twice. A role-manager call may already hit discord.js's cache; reduced invocation counts are not necessarily reduced REST calls.

The member resolver now builds its fuzzy index only when exact, prefix and substring matching all fail. This shared improvement benefits prefix moderation and utility commands that resolve names. Search limits, match ordering, ambiguity decisions and remote fallback remain unchanged.

Run `node work/performance/member-search-benchmark.mjs` after building to compare the saved pre-change member resolver with the current one. Twenty measured trials follow three warmups. On this Windows host with 5,000 cached members, cold exact nickname lookup measured 11.68 ms before and 6.15 ms after; warm exact lookup was 0.023 ms and 0.015 ms. Cold typo lookup was 51.74 ms and 52.66 ms, so no fuzzy-search speedup is established. Results are in `work/performance/member-search-results.json`.

The focused command snapshots in `prefix-before.json` and `prefix-after.json` use the actual custom `memberResolved` Sapphire argument. Prefix roleinfo's controlled handler median was 92.23 ms before and 61.76 ms after, with role-manager calls reduced from two to one. Those elapsed values include artificial boundary waits. Member-resolution calls fell from two to one in userinfo/userbanner, but their tiny local timings were noisy and do not establish a wall-time improvement. No production latency claim follows from these experiments.

## Correctness and limits

### Complete slash and prefix comparison

`node work/performance/command-benchmark.mjs all round-before.json` captures all 42 commands in both styles. After changing and rebuilding the bot, run the identical harness with `round-after.json`, then `node work/performance/build-speed-comparison.mjs`. The builder rejects missing, failed or mismatched scenarios and exports all four timings in both milliseconds and seconds to `work/performance/speed-comparison.csv`, with raw summary data and an interactive comparison alongside it. The baseline is the start of this pass and already contains earlier performance changes; it is not an invented measurement of the original bot.

This pass reuses resolved roles in `fadmin`/`fmod`, overlaps response delivery and case persistence after successful kick/softban actions, and overlaps the two independent log sends for kick/softban/unjail. Both response and case results settle before failure reporting, avoiding a delayed success overwriting an error. Softban's ban and unban remain ordered. The eight-trial median comparisons use identical fixtures and artificial waits; unchanged commands' differences are timing variation. In particular, the harness injects a wait into role-manager calls even when real discord.js may answer from cache, so removed manager calls must not be described as saved HTTP round trips or guaranteed production latency gains.

- Statistics and profile request sharing lasts only while the request is pending. Failures release the pending entry. Weak references do not retain departed guilds/users. Later statistics use the current member cache; later profiles request fresh Discord data.
- Autoresponder cache retains the existing 60-second TTL and 1,000-guild limit. Concurrent list calls share a query. Successful writes and guild removal invalidate both cache and pending read ownership, so a late read cannot repopulate the cache. Shutdown clears both maps. A caller whose read began before a write can still receive that earlier snapshot; subsequent callers refresh it.
- Purge limits individual requests to five per operation, including failed-bulk fallbacks. Multiple purge invocations can each have five workers. Discord's REST manager still controls actual rate-limit delivery. Bulk requests on the same channel are processed in order.
- Shared reply completion preserves V2 flags, visibility established by defer, and mention suppression. Already completed interactions still use follow-ups when needed. Existing permission and hierarchy decisions are not cached as authorization grants.
- Role search now uses current role and member data rather than retaining five-minute command-local results. Fuzzy role ranking uses actual Fuse scores. The `roleinfo` alias `role` remains shadowed by the primary `role` command, as Sapphire resolves primary names first.

Several larger concerns need separate behavior work rather than a speed claim: jail/unjail acknowledge success before all background changes finish; background moderation tasks are not a durable queue; warning modal authorization can still wait on a cold config lookup; permission mutation commands have existing read-modify-write races; regex case searches need production query plans before changing indexes. No production indexes or moderation state were modified in this pass.

Measure those routes using `durationMs` and a dedicated test guild before selecting another performance change. Preserve durable case/scheduler writes, actor authorization, hierarchy checks and ordered dependent Discord actions even when they add necessary latency.
